# Specific instructions to all AI agents

* ALWAYS make sure to follow the physics simulation as done in FSMP (https://github.com/DaymareOn/hdtSMP64) to ensure that you'll also simulate possible errors in the physics configuration (xml) correctly
* The same holds for CBPC (CBPC Physics with Collisions, Nexus mod 21224): its own code runs, with its configs as they are, including their errors
* NEVER introduce additional shapes or configurations for the physics simulation; just use what is there already
* NEVER implement workarounds or silent fallbacks in cases where the same thing would not work in-game either

## Keeping FSMP updates cheap

The SMP preview runs FSMP's own sources from `lib/hdtSMP64`. Updating FSMP must stay a pull + rebuild:

* FSMP's files are compiled **unmodified** (list in `src/fsmp/fsmp.cmake`: `hdtSkinnedMesh/*`, `ActorManager.cpp`, `hdtSkyrimSystem.cpp`, `hdtSkyrimPhysicsWorld.cpp`, `hdtSkyrimBone.cpp`, `hdtSkyrimBody.cpp`, `hdtDefaultBBP.cpp`, `config.cpp`, `Events.cpp`, `XmlReader.cpp`, ...), with FSMP's own `PCH.h` force-included. Do not port or copy them into `src/`.
* Not compiled: the game integration (`main.cpp`, `Hooks.cpp`, Papyrus and save-game code). `src/fsmp/StandIns.cpp` defines the few symbols of it that compiled files use (`OverrideManager`, whose overrides only Papyrus scripts and save games can set).
* Everything the standalone build needs from the game lives in fork-owned files under `src/fsmp/`:
  * `include/` — stand-in CommonLibSSE / SKSE / spdlog / Detours headers with the names and members FSMP uses. The scene graph types behave like the engine's: reference counting, world transform updates, the case-insensitive string pool, empty child slots after detaching, cloning.
  * `include-noppl/` (compilers without PPL) and `include-nowin/` (platforms other than Windows) — `ppl.h`, `d3d11.h`, `intrin.h` with the Win32 declarations FSMP uses. The PPL stand-in runs everything on the calling thread; `task_group::run` defers to `wait()` like PPL does. CBPC uses `include-noppl/` too (`concurrent_vector.h`, `concurrent_unordered_map.h`, `amp.h`).
  * `StandIns.cpp` — the stand-ins' behavior. Engine functions that can't exist outside the game (hooks, SKSE interfaces) log an error when called.
  * `FsmpScene.*` — the engine around FSMP: NIF → engine objects (`LoadModel`), equipping (`AttachArmor`: armor attach event, skin bound to the skeleton by bone name, attach event again), the FaceGen head (`AttachHead`: head skinning events), the inventory of equipped items (`SetWornItems`), frames (`Step`: frame event + frame sync event) and FSMP's plugin load (`Initialise`). The engine functions `ActorManager.cpp` calls through `REL::Relocation` (line of sight, FaceGen path, `NiStream`) are registered there.
* Bullet: `lib/bullet3` is checked out at the version of FSMP's vcpkg port (`cmake/ports/bullet3/vcpkg.json`). `fsmp.cmake` copies its sources into the build folder and runs the patch block of FSMP's `portfile.cmake` on them, so changes to FSMP's patch apply by themselves. The port's replacements are text searches; one that matches nothing leaves Bullet unchanged in FSMP's build as well, and CMake reports it (currently the non-Hookean spring calculation).
* After pulling FSMP: check out the Bullet version of its port in `lib/bullet3`, add new FSMP source files to `fsmp.cmake`, rebuild. Compile errors name the engine types or members a new FSMP version uses; add them to the stand-ins.
* If an FSMP file can't be used as-is, extend the stand-ins instead of editing the FSMP file. When an edit is unavoidable, keep it minimal and make it suitable for an upstream pull request. (The fork's older `HDT_SMP64_STANDALONE` compat layer in `lib/hdtSMP64` is not used: the build doesn't define the macro.)

## Keeping CBPC updates cheap

The CBPC preview runs CBPC's own sources. CBPC's license doesn't allow uploading them: they are not in the repository but in the ignored folder `lib/CBPC`, where the user unpacks the source archive of CBPC's Nexus page. Updating CBPC must stay: unpack the new archive there (replacing the old one), rebuild.

* `src/cbpc/cbpc.cmake` copies CBPC's files (`skse64/CBPC/*`) into the build folder and compiles the copies. The copies differ from the originals only by mechanical rewrites of Visual C++ syntax into standard C++ (backslashes in `#include` paths, `for each (x in list)`, constructor calls written `T::T(...)`) and by `cbpc::GameFileStream` in place of `std::ifstream` (finds the Windows paths CBPC builds without regard to case). Do not edit CBPC's files, and do not port or copy them into `src/`; extend the rewrites only with rules of that kind (syntax, not behavior).
* Not compiled: the game integration (`main.cpp`: plugin load and SKSE messages; `hook.cpp`, `hookD3D.cpp`: hooks). `src/cbpc/CbpcScene.cpp` does what they do in game: `Initialise` runs the plugin load and the data loaded message (configs) in `main.cpp`'s order, `Actor::Step` is the frame hook (`updateActors`). Compare them with `main.cpp` and `hookD3D.cpp` after an update.
* SKSE's own files that don't depend on the game are used as they are, from the archive: `skse64/NiTypes.h`/`.cpp` (math) and `skse64_common/skse_version.h` (the version macros choose CBPC's code paths). The game version macro comes from the archive's `sheets/Runtime.props`.
* Everything else CBPC uses from the game and SKSE is in fork-owned files under `src/cbpc/`:
  * `include/CbpcGame.h` — stand-ins for the SKSE headers CBPC includes, with SKSE's names and members. CMake generates a header for every `skse64/`, `skse64_common/`, `common/` include of CBPC's files that includes `CbpcGame.h`. `include/common/` holds SKSE's prefix header (forced into every CBPC file, like CBPC's project does; the standard headers come before `Windows.h`, whose `min`/`max` macros CBPC uses) and fixed-size `UInt32` & co.; `include/dirent.h` replaces CBPC's Win32 `dirent.h` (NTFS order, any case); `include-nowin/` has the Win32 declarations CBPC uses (and `clock()` in milliseconds, see `IPrefix.h`).
  * `StandIns.cpp` — the stand-ins' behavior, following SKSE's sources (`GetWornForm`, `VisitFactions`, `GetKeyword`, …). Forms are built from `cbpc::GameData` (the previewer's engine records) when CBPC first asks for them. Engine functions that can't exist outside the game (scripts, SKSE messaging, INI settings, unknown game addresses) log an error when called.
  * `CbpcScene.*` — the engine around CBPC: player, interior cell, process manager listing the actor, the actor's reference, the mirror of the actor's 3D, equip events. The game addresses CBPC reads through `RelocPtr` (process manager, frame time) are registered there by their offsets for the code paths the version macros choose; an address that isn't registered is logged.
* Visual C++ gives global variables a symbol with their type; when two CBPC files define a global of the same name with different types, list it in `CBPC_SAME_NAMED_GLOBALS` (`cbpc.cmake`) so other compilers link them apart.
* After unpacking a new CBPC version: rebuild. Compile errors name the SKSE types or members it uses (add them to the stand-ins), link errors name globals defined twice (see above), the log names game addresses it reads (register them). Without `lib/CBPC` the build uses `CbpcUnavailable.cpp`.
